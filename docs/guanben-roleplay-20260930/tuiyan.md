## 〇、拍板记录（同志 2026-11-05）

1. **治本，不止血。** 重新设计过回合推演的内容；之前提的「三批止血」和「先判决后成文」作废。
2. **数分两类。** 银两、兵额、人口、日程由 AI 写实数，账本验；抽象指数 AI 只写方向、程度和原因，代码按性情折算。
3. **引擎先走。** 确定性结算先跑完，AI 在结算后的世界上办事。
4. **成文从简。** 时政记、实录、史臣曰一次写成；后人戏说点开才生成。
5. **走官本位路线。** 这次重做就是路线第一刀：事的底座只建一次，钱粮竖切在后，新前端改读新数据。
6. **办到完为止。** 一次生成被截断或断掉，就自动开新调用接着办，直到任务完成。
7. **即时制。** 时间像 EU4、CK3 那样连续走；玩家走到想要的时间点，按「推演」才出 AI 大推演。
8. **时间不倒流。** 后果从按键当日起生效，经过可以回溯着写，已记录的是既成事实，远方的事可以写成「早已发生，今日才知」。
9. **史记只写已传到的事。** 只写已传到视角人物处的事；还在路上的，到了才进案头，下次史记才写。
10. **对照实验放最后。** 用同志专门开的、设了限额的 key。
11. **Agent 模式是失败的，远不如 LLM 模式。** 写得薄、文气差、世界不动、数据乱，四样都有。重做不能走它的路。
12. **世界的反应以人物为出发点。** 实体是人物，让 AI 扮演他们。
13. **每个人是一个实体。** 要和游戏其他机制接上，不能做成分裂的人，同一个人人格统一。
14. **第十七章五问按推荐（11-06）。** 要事的经手人第一版不扮；人只声明、全知的裁决定结果；每 30 日 24 人、一人一次调用；百姓、天灾由裁决和引擎写；人物实体八处全接，一个机制一片。
15. **实验模型由我挑（11-06）。** 同志给了 key 和中转地址，说「模型你自己挑着用」。

## 一、病根和教训

### 1.1 三个症状，分别有什么证据

**常失败。** 09-21～22 的日志里有 12 次报错：主写回整批失败 4 次、主推演超预算被拒 3 次、存档 2 次、网络、复核预算、代码错误各 1 次。这些是修 bug 期间、第 1 回合的样本，比例不代表现状。

**耗时久。** LLM 模式成功回合 5.3～6.3 分钟。一个真实回合调用 26 次，请求约 178 万字，输出约 8.8 万字。主推演一次请求约 28 万字；另有 9 次调用各超 10 万字。

**说的和数据对不上。** 三个实验（用真代码，不调模型）：

| 实验 | 结果 |
|---|---|
| 真写回器，3 条写入 1 条坏 | 整批撤销：国库仍是 1000，忠诚仍是 50。去掉坏条目才落账（777、88） |
| 真 `writeBack`，写回器打桩为失败 | 叙事写「斩乙」，死亡处理跑了 0 次，乙仍活着，叙事照常保留 |
| 真聚合 | AI 写全国民心 80，回合末变回 60 |

第二个实验走的是主干现行路径：一条写入失败，整批回滚（`modules/ai-change-applier/reconcile.js:1584`），抛错跳出 `writeBack`（`tm-endturn-apply.js:188`），其后 68 类结构化字段和死亡处理都不执行，再由 `recoverMain` 保留叙事照常提交（`tm-endturn-validity.js:95`），而 `mainWriteback` 还记成 `ok:true`（`tm-endturn-ai.js:4903`）。这条路是 09-21 为修「过回合失败」改出来的：失败变成了静默不一致。

### 1.2 五条根

**根一：推演里没有「事」。** AI 的产出按 97 个字段组织，不按事组织。真实一回合的主推演里，客氏一个人写进 18 个字段，胡廷宴 11 个，东江饷司 14 个，而且同事异辞：胡廷宴在人事字段是「停掌抚赈，留任待勘」，在官制字段是 `demote`，在时政记是「革其督抚职掌之半，降格留任候勘」。叙事和数据是同一次调用里并排写的两样东西，中间没有因果，天然会对不上。

**根二：同一个数有两个主人。** AI 能写，引擎也算。全国民心就是例子：AI 写了，回合末被地块聚合盖掉（`tm-integration-bridge.js:622`）。

**根三：每回合把天下重想一遍。** 没有「这件事办到哪了」。5 月实测，5.48 万字的系统提示重复 18 次，占输入 69%。

**根四：未结的事散在十几套账里。** 诏令、时局要务、承诺、阴谋、伏笔、民变苗头、驿路阻断、廷议待议……各有各的存储和格式（3.1 节列了 18 套），AI 得在每一套里分别想起来，再分别写回。

**根五：同一个人被拆成好几个。** 问对、常朝、廷议、奏疏、书信、NPC 自主、势力调度、主推演各拼各的人格（7.2 节），势力调度甚至不是让 AI 当这个人，而是「你是历史推演大师」（`tm-faction-npc-llm-decision.js:1543`）。同志 7 月就报过「跨界面人格分裂」，当时只统一了记忆来源。

其余的臃肿几乎都是事后补这几条缝：38 个模块、4 万余行、1043 个 `try`、1055 个 `typeof` 判断、至少 7 层修复。这里不再加第 8 层。

### 1.3 Agent 模式为什么失败

同志的判断是它远不如 LLM 模式：写得薄、文气差、世界不动、数据乱，四样都有。从代码看，它败得很有教益，因为**它的知识和 LLM 模式同源**：依据直接复用 LLM 的 `sysP + tp`（`tm-endturn-agent-mode.js:451-462`）。同样的知识，产出却薄得多，差别只能在别处：

| Agent 模式的做法 | 后果 |
|---|---|
| **叫模型忽略输出结构**（「凡必须填写 XX 字段……你一律忽略」，`:460`） | LLM 模式的字段逼着模型每个面都想一遍；去掉之后，广度只靠软提醒，后来加的门禁也逼不回来 |
| 让模型自己决定查什么、干什么 | 预算花在读档和选工具上 |
| 每轮输出上限 2400 token 起、每轮至多 6 个工具、12 轮（`:949`、`:1009`） | 写不长，也写不多 |
| 写工具只有 19 个左右的语义工具 | 暗手、风闻、书信、势力暗流这些世事没有地方写，只能靠事后的 `deepen_*` 重述提示词来补。6 月它自己的审计也承认这些「完全没产」（`docs/agent-mode-depth-gap.md`），后来补了工具，同志的结论仍是远不如 LLM 模式 |
| 专精调用降级成可选的事后工具 | 失去专精的深度，提示词还会和 LLM 版漂移 |
| 允许按路径直接写字段（`set_field`、`adjust_field`、`edit_world`），写引擎的账还打「覆写」标让引擎让步（`_markOverride`） | 绕开了领域规则。这可能是数据乱的原因之一，未实测 |

**教训：世界活不活，主要取决于产出结构逼模型想多少面，不只取决于喂了多少知识。另外，它每次写入都有回执，数据照样乱，可见有回执不等于数据不乱。所以本稿走 LLM 的落地代码，并在实验里直接查存档（14.3 节）。**

### 1.4 所以：LLM 模式是地板

LLM 模式的问题在组织方式，不在手艺。它有四样资产，这次都留：

| 资产 | 具体是什么 | 怎么留 |
|---|---|---|
| **提示词里的规矩** | `tm-endturn-prompt.js` 里 700 多段拼接：阻力原则、次生反应、官员任免铁则、费效为度、隐藏议程、危机分岔、势力矩阵、行文指纹、时间粒度…… | 移植，不重写。第一版整份带上，有证据才裁 |
| **逼出来的广度** | 输出结构要求每个面都有产出。09-21 真实一回合：16 条势力暗流、19 条军事行动、13 条风闻、16 条暗手（7.9 节） | 保留输出结构：每个上场的人、每个势力都要有产出，代码逐项核对 |
| **专精视角** | sc15 只想人物，sc18 只想军事，一次只盯一个面 | 人物的部分交给人物自己（第七章）；军事、势力的硬核规矩移植给裁决 |
| **落地代码** | `applyAITurnChanges`、`writeBack` 的 90 多类字段落地，天天在跑 | 不另造写工具，改成小批调用（5.1 节，已实测） |

**铁律：LLM 模式有的产出，默认都留；要裁一样，得有对照实验的证据。**

**换的是这几样**，它们才是病根：

| | 旧 | 新 |
|---|---|---|
| AI 的工作单位 | 一整块 97 字段 | 一件一件的事，一件一卷 |
| 叙事和账的关系 | 并排写，没有因果 | 同卷写，回执对得上才算办完；史书最后只读办完的事 |
| 失败的范围 | 一条坏，整批撤；跳过后面所有字段 | 一件坏只坏这一件，退回重办 |
| 中断 | 整块重来或靠修复 | 已交的卷算数，断了开新调用接着办 |
| 未结的事 | 十几套账，每次重想 | 一个册子，事自己记着办到哪 |
| 同一个数 | 两个主人 | 一个主人 |
| 同一个人 | 各机制各拼一份 | 一个实体，全游戏同一份人格和记忆 |

这算不算换皮，请同志判断。我的看法是不算：范式是 AI 怎么工作、因果怎么走、失败怎么算，这些全换了；提示词手艺和落地代码相当于引擎，留下不等于留下旧范式。

**和 Agent 模式还相同的两处**，要明说：引擎先走（同志已拍，即时制下本来就是这个顺序），先写账后成史。我判断这两处不是它失败的原因，因为现在 LLM 模式的时政记（sc1d）也是在主推演之后写的，质量是好的。但这只是判断，对照实验要专门看。

## 二、新流程全貌

**一句话：世界的变化全部来自事。AI 不再「写这一回合」，而是一件一件办事，办完一件落一件账；再由 AI 扮演一个个人物，各凭所知作出反应，由裁决定结果；最后只照着办完的事写史。**

```
玩家按「推演」，时钟停在当日
  │
  ├ 立案（代码）     把这段时日该办的事排成案单，每件配好案卷
  │
  ├ 办事（AI）       先开卷：通盘想一遍矛盾、后果、谁会动（接替 sc0、sc05、sc1q）
  │   │              再逐件交卷：经过如何、账上动什么、人有何反应（接替 sc1）
  │   │              能一次调用办完就一次办完，断了就接着办
  │   └ 落账（代码） 收到一卷就走 LLM 的落地代码，出回执，对得上才打勾
  │
  ├ 余波（AI）       人物上场：AI 扮演一个个人，各凭所知拿主意，只声明打算
  │   │              （接替 sc15、sc1b，以及 sc1c、sc16、sc18 里人的部分）
  │   ├ 裁决（AI）   全知的主持人定结果：谁撞上谁、成没成、损失多少、谁察觉；提新事
  │   └ 落账（代码） 同上
  │
  └ 成史（AI）       只读已传到视角人物处的事和最终数字（接替 sc1d）

推演后后台：记忆回写、人物认知、记忆合成、文事（照旧，只是改读卷）
```

**术语**：**案单**是这次推演要办的清单；**案卷**是代码给 AI 准备的一件事的材料；**卷**是 AI 对一件事交的答卷；**回执**是代码对卷里每条账的处理结果；**上场**指这次推演由 AI 扮演这个人；**裁决**是定结果的全知调用。

**这样治五条根**：叙事和账写在同一件事里、对上了才算办完（根一）；每个数只有一个主人（根二）；事自己记着办到哪，提示词的固定部分只有一份（根三）；未结的事进一个册子（根四）；每个人是一个实体（根五）。

## 三、立案

全部由代码完成，不调模型。

### 3.1 案从哪来

事沿用主稿 3.1 节的 `GM.matters`。旧的十几套账第一版不动，由适配器读进来。因为账行走的就是 LLM 的字段（5.1 节），这些旧账会被原有代码照常更新，旧界面的面板照常能看。等新前端改读 `GM.matters`，它们再逐个退役。

| 来源 | 现有存储 | 怎么立案 |
|---|---|---|
| 玩家的诏令 | `GM._edictTracker`、`GM._edictLifecycle` | 一道诏一件，**必办** |
| 问对、密诏里的承诺与命令 | `GM._npcCommitments`、`GM._wdRewardPunish` | 挂到相关的诏令上；没有就自成一件，必办 |
| 时局要务 | `GM.currentIssues` | 一条一件，或并入相关诏令 |
| 待议、奏疏未决 | `GM._pendingTinyiTopics`、`GM.memorials` | 玩家批过的进案，没批的留案头 |
| 战事 | `GM.activeWars` | 一场一件 |
| 阴谋暗流 | `GM.activeSchemes`、`GM._hiddenMoves` | 到期的进案；其余由当事人上场时自己接着谋 |
| 民变苗头、驿路阻断 | `GM._revoltPrecursors`、`GM._routeDisruptions` | 过显著度线的进案 |
| 伏笔 | `GM._foreshadowings` | 到期的并入相关的事 |
| 剧本事件 | `GM._candidateEvents` | 触发条件满足的进案 |
| 账本信号 | 引擎这段时日的事件日志 | 亏空、欠饷、灾伤、缺官，过显著度线的进案 |
| 已在办的事 | `GM.matters` | 到了 `nextDay` 的进案 |

人物的主动行动（`GM._npcActionLedger`）、势力的决断（`GM._sc16FactionDirectives` 与势力调度结果）、到达的书信（`GM._pendingNpcLetters`、`GM._pendingNpcCorrespondence`）不立成要事，是当事人上场时的材料（第七章）。

事的数据形状只比主稿多三个字段：`nextDay`（下次看它的日子）、`waitingFor`（在等什么，如「客粮抵西安」）、`volumes`（历次的卷，近两卷留全文，更早的压成一句）。`chain`（分派结果）第一版可以空着，分派片上线后再填，不用迁移。

### 3.2 并案

一道诏和一条时局要务常常是同一件事。代码先按共同的人名、地名、诏令编号找候选（现成的 `_tcScanMentionedNames`，`tm-ai-infra.js:2318`；要务和诏令已有 `linkedIssue`），明显重合的直接并。

拿不准的不硬并，交给开卷：AI 通盘看过案单后可以建议并案；办事时也可以声明「这件一并办了」，程序核对后把另一件打勾。

### 3.3 排序

- **必办**：玩家的令。件数不设上限，都要办。
- **择办**：其余的事按主稿 3.2 节的显著度排序，每 30 日取 8 件、一次至多 20 件〔初值〕。
- **没选上的**：这次不动，留在案上；过了期限的标「逾期」。钱粮竖切之后，这一档才由胥吏「依例」办掉。

办事的顺序：先玩家的令，再按显著度；有因果的排在一起。

**卷的长度不设上限。** v1 给每档设了字数上限，这是错的，压的正是 LLM 模式的长处。输出额度沿用现有主推演的设置（`_sc1BaseTok`）。

### 3.4 案卷

**固定部分**：第一版整份沿用 LLM 的 `sysP`（5.48 万字：剧本总述、势力、人物、地名、官制、隐藏议程、危机分岔和全部规矩）。一次推演内逐字不变，能走缓存的走缓存（`buildCachedMessages`，`tm-ai-infra.js:414`）。要不要裁，由实验决定（14.2 节）。

**每件的案卷**：

| 段 | 内容 | 来自 |
|---|---|---|
| 来由 | 诏令原文、问对要点、奏疏摘录 | 原存储 |
| 办到哪了 | 上次的卷（近两卷全文，更早的一句一件） | `matter.volumes` |
| 人 | 经手人、利害人的底子 | `TM.Person.brief` 的精简档（7.2 节），和问对里是同一份 |
| 账 | 和这件事相关的数：地块、军队、财政条目 | 现有提示词的相应段 |
| 记忆 | 按这件事的人名、地名检索的前几条 | `TM.MemoryRetrieval`、`TM.MemoryContextCompiler` |
| 路程 | 相关地点之间的日数 | `TM.MapRouteDays` |
| 已记事实 | 相关人物最后一次留下记录的日子（时间不倒流用，10.2 节） | 各记录 |
| 可用字段 | 这件事用得着的账行字段和写法 | 现有 schema 说明，按领域取 |

### 3.5 例子：天启首回合的案单

| # | 件 | 并进来的 |

## 四、办事

### 4.1 开卷

办事的第一次调用，先通盘想一遍。它合并 sc0（局势分析）、sc05（因果回顾）、sc1q（对话承诺）的产出结构：矛盾、后果、谁会动、势力动向、阶层不安、财政压力、承诺该兑现什么、并案建议。

这些旧调用每个都带十几万字的请求，产出却只有两千字上下。合成一次，产出不少，请求要小得多。开卷的结果放进后面所有调用，也是统一全局判断的地方。是否必要由实验验证（14.2 节）。

### 4.2 一次办多少

**默认能放多少放多少，最好一次调用办完全部要事。** 这样和现在的主推演一样，是同一个头脑通盘写，不会一件一件想散。窗口小的模型、被截断的情况才分批，由第六章的循环接上。

这是和 Agent 模式最根本的差别：不是把思考切碎，而是**同样一次想完，只是边想边交，断了不全废**。

### 4.3 交卷格式

不用一整块 JSON。一整块 JSON 断在中间就全废，文言长文里还容易混进没转义的引号，现有的修复层大半是为它写的。新格式是**有开有合的文本块，账目一行一条**：

- 收到 `卷毕` 才算交卷，半截的卷不会被当真；
- 一行账写坏了，只坏这一行；
- 走流式，收到一卷就处理一卷。现有流式入口已有 `onChunk`（`tm-ai-infra-retry.js:442-501`），不支持流式的中转也能回退成一次性返回。

样例如下。账行内容取自 09-21 真实输出，其余是我手写的示意，不是模型产出，日期也是示意：

```
<<<卷 m-陕西粮饷
```

| 段 | 写什么 | 谁读 |

| 账 | 实数和硬操作，一行一条 LLM 的字段条目（`f` 是字段名） | 落账 |

| 人 | 谁有什么心绪，记住了什么 | 写进人物记忆（第九章） |
| 回报 | 谁从哪里报了什么，可以和实情不同（8.3 节） | 代码算到达日；到了才给成史和案头 |
| 风声 | 外人能听到什么：公开的部分，从哪传出，传多广 | 代码按路程算谁何时听到（7.4 节） |
| 下一步 | 过多少日再看，在等什么 | 代码写 `nextDay`、`waitingFor` |

### 4.4 办事的规矩

现有提示词的规矩全部沿用（阻力原则、次生反应、任免铁则……）。只改两处明显不再适用的：不再要求输出 97 字段的整块 JSON；不再要求一次写时政记。新增四条：

1. **经过里的硬事实必须有账。** 硬事实指任免、生死、下狱流放、钱粮实数、兵额、地块归属、宣战议和、营造。没有账行，就不许写成已发生。心绪、气氛、议论不算硬事实。
2. **过去不能改。** 见 10.2 节。
3. **人要在册。** 只能动名册里的活人；要新人物走生事闸（7.7 节）。
4. **有人才有事。** 经手人是谁、他为什么这样办、谁得利谁受损，都要写出来。

## 五、落账

### 5.1 走 LLM 的落地代码，只是改成小批

v1 想用 Agent 模式的写工具，这是错的。那些工具只有 19 个左右，覆盖不了世事，也从没经受过真实游玩。

新做法：**账行就是 LLM 字段的一条，每卷组成一个小 `p1`，走原来的 `applyAITurnChanges` 和 `writeBack` 字段块。** 语义和现在完全一样，只是粒度从一回合一大批变成一卷一小批。这样也不用新造写工具，人物死亡这类写口都现成。

**已用真代码实测**（2026-11-05，脚本在会话临时目录，未入库）：

| 实测 | 结果 |
|---|---|
| 同样 2 好 1 坏，改成一条一小批 | 好的落账（国库 777、忠诚 88），坏的单独报「path not declared in state schema」 |
| 真 `writeBack`：第一件含坏条目，第二件写斩乙 | 第一件单独失败，第二件通过，乙 `alive=false` |
| 真实存档（GM 11.1MB）上一小批的耗时 | 约 150～190ms，主要是整份快照 |

第 1.1 节的前两个实验，这样就翻转了。

**要动的代码**：`writeBack` 头尾有一些一次推演只该跑一次的事（`ActionLedger.advance`、`PoliticalActions.migrate`、`EdictEffects.begin` 与 `finish`、`ClassEngine.finalizeTurn`、`_applyPostValidateAssemble`）。把它们拆到推演开始和结束，中间的字段块按卷调用。专精调用自己的落地函数（如 `_applyNpcDeepResult`、`applyAIArmyChange` 的调用处）从 `tm-endturn-followup.js` 搬出来，走同样的路。

**粒度**：先一卷一小批，失败了再把这一卷逐条重放，找出坏的那条。天启一次推演约 30～40 卷，快照合计约 7 秒，可以接受。绍宋存档大得多，要实测；如果太慢，改成只拍这批字段涉及的根字段。

### 5.2 对得上才打勾

一卷要打勾，得同时满足：

- **账全成**：`applied.failed` 为空；
- **经过与账相符**：小批的 `narrative` 就填这卷的经过，现有校验器（`modules/ai-change-applier/validators.js`）照常扫。

不满足，这件就**退回重办**，和下一批一起发回给 AI。发回去的只有这一件的经过、回执和问题，比如：

> 经过写「发银十万」，回执：太仓只剩三万，支不出。要么改少，要么写明支不出，后果如何。

- 已成功的账不重做（靠 `effectId` 或 `id` 防重复）。
- 校验器扫叙事得出的只是怀疑（代码注释也这样说：「hypotheses, not proof」）。旧路径里它们曾让整批回滚；新路径里只触发一次退回。
- 退回至多 2 次〔初值〕。还不符，就以回执为准：没落账的那条标「未成」，卷打勾但记一笔，成史时按「未成」写。**宁可事办得不圆满，也不能让史书写没发生的事。**

### 5.3 撞车

两件事争同一笔钱、同一支兵、同一个人时，后到的一件会收到回执「不够了」或「此人已被调走」。这不算错误，退回给 AI 让它写成世事：户部支不出、两路争饷。这正是旧格式写不出来的硬核感。

### 5.4 每个数只有一个主人

| 数 | 主人 | AI 能做什么 |
|---|---|---|
| 国库、内帑 | 财政引擎账本 | 写实数（`fiscal_adjustments`），余额不够就退回 |
| 兵额 | 军队账 | 写实数（`army_changes`） |
| 人口 | 户口账 | 写实数，不超过该地现有人口 |
| 带单位的剧本变量（如辽饷积欠「万两」、流民「口」） | 变量 | 写实数，夹在变量上下限内 |
| 日程、期限 | 代码按路程算 | 提议日数，不得短于路程 |
| 0～100 的剧本变量（如党争烈度） | 变量 | 只写方向和程度 |
| 人物的忠诚、压力、野心、好感 | 人物 | 只写方向和程度 |
| 地块民心、繁荣 | 地块 | 只写方向和程度 |
| 皇威、皇权 | 各自引擎（如 `adjustHuangwei`，`tm-authority-engines.js:212`） | 只写方向和程度，代码折算后以「来源」身份记入 |
| 全国民心等聚合量 | 派生量，由地块聚合 | **不能直接写**。要动全国就写「天下」，代码按人口权重摊到地块 |

带不带单位，剧本数据里本来就分得开（实存档的 21 个变量里，带单位的 4 个，其余是 0～100）。

### 5.5 抽象指数怎么折算

```
增减量 = 基数(程度) × 性情系数 × 余量系数
  基数：轻 2，中 5，重 10，极 18
  性情系数：夹在 0.6～1.4，只对人物；如忠诚下降时，记仇、多疑者放大，宽厚、隐忍者缩小
  余量系数：越靠近上下限越难动，夹在 0.3～1
```

以上都是〔初值〕，影子运行时校准。算出来的数填进 `char_updates` 等原字段，走原来的落地代码。回执写明结果（如「魏忠贤 忠诚 62→54，重，收回批红」）。AI 决定谁、往哪动、为什么，代码只管尺度。这不是用公式写剧情：剧情在 AI 写的原因里，公式只是一把刻度尺。

## 六、办到完为止

### 6.1 循环

```js
while (案单上还有没打勾的) {
  批 = 取下一批(字数预算)           // 含退回重办的；默认放到预算用完
  开一次流式调用，边收边解析：
    收到一卷 → 落账 → 对得上就打勾、写日志 → 进度 +1
  调用结束 → 按 6.2 节判定怎么结束的 → 决定等待、减批或停止
}
```

**办没办完只看案单，不看模型怎么说。** 模型说「以上办完」但案单上还有，就开新调用接着办，不算失败。上场的人、裁决、成史都走这同一个循环。

新调用看不到上一次的全部思考，只看到开卷结论、已办摘要和回执。这是代价：分批时后面的事可能和前面接得松一点。所以默认尽量一次办完（4.2 节）；够不够，由对照实验读出来。

### 6.2 一次调用可能怎么结束

| 结束方式 | 已闭合的卷 | 下一步 | 计不计次 |
|---|---|---|---|
| 正常，案单办完 | 算数 | 进下一步 | |
| 正常，案单没办完 | 算数 | 开新调用 | 没交成一卷才计 |
| 输出上限截断 | 算数，半截的丢弃 | 开新调用，批减半 | 同上 |
| 超时 | 算数，半截的丢弃 | 开新调用，批减半 | 同上 |
| 收到一半断流 | 算数，半截的丢弃 | 等网络恢复后开新调用，批减半 | 同上（已花了钱） |
| 连不上，一个字节没收到 | 无 | 等网络恢复，定时探一次 | **不计**（没花钱） |
| 429、5xx | 无 | 按对方给的时间等 | **不计** |
| 上下文超长 | 无 | 批减半 | 不计，批到 1 件还超长就裁案卷 |
| 拒答 | 算数 | 把这一件单独拿出来试 | 计这一件 |
| 全文解析不出一卷 | 无 | 重申格式，批减半 | 计批内第一件 |
| 401、402、403、404 | 算数 | **立刻停**，提示玩家修 | |
| 玩家喊停 | 算数 | 停 | |

错误分类用现成的 `_tmAiErrHuman`（`tm-ai-infra.js:723`）和 `ai-text-truncated`、`ai-text-refused`（`tm-ai-infra-json.js:78`）。

### 6.3 「完成为止」的三个例外

1. **重试没用的错**（密钥失效、余额不足、模型名错）：立刻停，已办的保留，修好可以接着办。
2. **同一件连续 3 次办不出来**〔初值〕：这件留在案上，记「尚无回奏」，其余继续，下次推演再办。
3. **玩家喊停**：随时。

**这个循环一定会停。** 每一轮花钱的调用，要么至少办完一件，要么给某一件记一次。每件至多记 3 次，退回至多 2 次，所以花钱的调用不超过件数的约 6 倍。不花钱的等待可以无限长，但玩家随时能停。总量默认不设上限，界面显示已用的调用数和 token；设置里可以另设上限（默认不限）。

### 6.4 批和并行

- **批**：默认放到 `getPromptBudget` 给的预算用完。截断一次就减半，成功几次再慢慢放回。
- **并行**：要事默认 1 路（同一个头脑）；人物层并行，路数由实验定。并行时撞车靠落账解决。安卓照现有串行护栏只走 1 路。

### 6.5 中途关游戏

每收到一卷，就把卷的原文写进推演日志（沿用 `tm-endturn-recovery-vault.js` 的做法：放 IndexedDB，只存模型的回答，不存提示词和密钥）。

重开游戏时，如果日志和存档对得上（世界指纹相同），就提示「上次推演未完，已办 7/12 件，是否继续」：

1. 读回按键前的存档；
2. 按原顺序把已交的卷重放落账，不重新调模型；
3. 接着办没打勾的。

重放的回执和原来不一样时（比如引擎用了随机数），以重放为准，并记一笔。

### 6.6 玩家看到什么

- **进度**：「已办 7/12 件」，加上当前这件的标题。只显示玩家本来就知道的事的标题；人物层只显示「朝野动向」「诸方动向」这样的总名，不剧透。
- **用量**：已用调用数和 token。
- **停止后的三个选择**：
  - **继续**：接着办；
  - **就此收束**：没办的留案，已办的写史；
  - **撤回整次**：回到按键之前。
- **成果**：史记旁边显示「办 12 件，落账 41 条，未成 3 条」，点开能看每条未成的原因。

## 七、余波：人物上场

> 同志 11-05 定：世界的反应以人物为出发点，实体是人物，让 AI 扮演他们；要和游戏其他机制接上，不能做成分裂的人，每个人是一个实体。v2 的「五司」作废。

全部要事办完后，世界开始反应，也接着自己走。**这一步是世界活不活的主体。**

### 7.1 为什么以人物为实体

五司还是一支全知的笔，按领域替所有人写：崔呈秀怎么想、皇太极怎么动，都是它一口气编的。换成人物，好处有三：

- **有人味**：每个人按自己的性情和处境拿主意。问对一直是游戏里 AI 最入戏的地方，这里用的是同一套手艺。
- **信息差自然就有了**：毛文龙没接到敕书就不会反应；崔呈秀不知道黄立极在背后使绊子，两人才斗得起来。
- **和路线一致**：主稿的总纲就是「每件事的结果都是有人做了选择」。

09-21 的真实产出其实已经几乎都是人的故事，比如暗手写的是「崔呈秀：因客氏下狱……→夜遣心腹校尉销毁册籍→图谋自保」，军事行动写的是「德川家光下达……」「林丹汗集结……」。差别只是现在由全知的笔代写。

**零件大多现成，只是一直闲着：**

| 要用的 | 现成的 | 现状 |
|---|---|---|
| 怎么扮 | 问对提示词 `_wdBuildPrompt`（`tm-wendui-persona-views.js:261`）：性情、年岁、家族、近事、人际、记忆、文事 | 只在玩家问对时用 |
| 他知道什么 | `TM.LiveContext`（公开事实加本人回想，文件头写明「No hidden-world dump」）、`buildNpcBehaviorContext(npc)`（本人、职任、计划、记忆、承诺） | 有，未接消息路程 |
| 他能做什么 | `NpcBehaviorRegistry` 的 30 来种行为；`TM.NPC.ActionLedger.execute` 查身份、权限、钱，出回执 | 有 |
| 现在用了多少 | `executeNpcBehaviors` 每回合至多 3 次模型调用，官位高、有野心也不触发（`tm-npc-decision-ai-driven.js:741`） | 几乎没用上 |

### 7.2 每个人是一个实体

**现状：同一个人被拆成好几个。** 凡是要 AI 以某人说话或行事的地方，都各拼各的：

| 机制 | 他的「人格」从哪来 | 记忆从哪来 |
|---|---|---|
| 问对 | `traitIds` 或 `personality`，加压力、近事、人际、外貌、家族、文事（`_wdBuildPrompt`） | `getMemoryContext` 加往次问对 |
| 常朝 | `personality`、特质、忠诚清廉野心、`aiPersonaText`（`tm-chaoyi-changchao-adapter.js:874`） | 记忆片段 |
| 廷议 | 有 `aiPersonaText` 用它，否则 `personality`（`tm-chaoyi-tinyi.js:596`） | `getMemoryContext` |
| 奏疏 | `traitIds` 或 `personality`，加 `personalGoal`（`tm-memorials.js:269`） | `getMemoryContext` |
| 书信 | 8 维性情折成的短语（`getCharacterPersonalityBrief`，`tm-hongyan-office.js:1535`） | `getMemoryContext` |
| NPC 自主 | `personalGoal`、`innerThought`、特质（`buildNpcBehaviorContext`） | 直接取 `_memory` 前 12 条 |
| 势力调度 | 势力数据里的「主君」`ruler.personality`；AI 的身份是「历史推演大师」，不是这个人（`tm-faction-npc-llm-decision.js:1543`） | 势力记录 |
| 主推演专精 | `personality`、`personalGoal`、`speechStyle`（`tm-endturn-followup.js:577`、`:2737`） | 记忆门槛切片 |

连「他怎么说话」都有两个字段：人物全档里的 `diction` 和补全时写的 `speechStyle`。

于是同一个人换个场合就可能换个性情；他在推演里暗中做的事，问对时的扮演者未必知道；他在问对里答应的事，推演里未必记得。同志 7 月报过的「跨界面人格分裂」就是这个，当时只统一了记忆来源，人格来源还是分裂的。

**新规矩：一个人只有一份「他是谁」。** 凡是 AI 要以这个人说话、行事，都走同一个入口：

```
TM.Person.brief(人, { 场合, 话题, 详略 })
  人格核    性情、口吻、人生底色、所求、只属于他的隐藏议程
  处境      现职、所在、羁束、家族、党派、手上的权与钱
  记忆      getMemoryContext，加按话题回想（TM.PersonalMemoryRecall）
  心里有数  上次打算什么、正在暗中做什么、答应了谁什么、最近收到什么消息
  场合      问对、朝会、奏疏、书信、推演：用什么格式，对谁说，能说多实
```

- **人格核只有一个来源。** 把现在的 `personality`、`traitIds`、`aiPersonaText`、8 维性情、`diction`、`speechStyle` 按固定优先级合成一份，所有地方一字不差。以问对的版本为底，它最成熟。
- **场合只决定怎么说，不决定他是谁。** 御前谨慎，私信直言；性情和心事是同一个。
- **详略分档。** 朝议一场十几个人，用精简档（人格核加最要紧的心事）。7 月修人格分裂时就得出过这个结论。
- **不新建存储。** 东西还在人物身上和现有的账里（`ch._memory`、`innerThought`、`personalGoal`、`GM.activeSchemes`、`GM._npcPlans`、`GM._npcCommitments`）。`brief` 是唯一的读法。写也照旧走 `NpcMemorySystem.remember`（已有 54 个文件在用），各机制写的记忆本来就在一处。
- **人可以变。** 压力、经历会改变性情（现有 `personalityEvolution`、`stressTrait`）。变了就是这一个实体变了，所有地方同时看到。
- **玩家也是一个实体**，只是他的主意由玩家拿。将来换人扮演，实体不变，只是换了谁拿主意（主稿第九章）。

这样才连得起来，比如：

- 崔呈秀上场时暗中烧了册子。玩家召他问对问边饷，扮他的 AI 知道这事（只有他和心腹知道），可以抵赖，可以慌，口吻还是他的。
- 问对里玩家敲打了他。下次他上场时记得，会据此动作。
- 廷议上他反对某议。之后的奏疏、私信里他知道自己说过什么，可以一致，也可以有意两面。
- 皇太极在势力调度里定的方略，就是他本人的决定，下次他上场时认这个账。

案卷里的人物底子（3.4 节）、裁决读到的人物，也都走 `brief`。

### 7.3 谁上场

代码选人，按下面的次序取满为止。每 30 日 24 人、一次至多 40 人〔初值〕，深度档可调。

1. 这次要事里被点名的利害人：魏忠贤、胡廷宴、毛文龙……
2. 该动的人：现有规划触发（`_npcCollectPlanningTriggers`）、到期的阴谋、未了的承诺、刚收到信的人。
3. 各势力至少一人。实存档 22 个势力都有在册人物：首领对得上名册的（皇太极、林丹汗、郑芝龙……）由首领上，对不上的（如「黑龙江、乌苏里诸部酋长」）由本势力地位最高的在册人物代言。远方的小势力可以轮流上。
4. 党魁、主将：韩爌、孙承宗……
5. 和视角人物有亲故关系的人。
6. 轮换几个小人物，让世界不只围着大事转。

玩家的人物不扮（现有规矩：禁止替玩家作决定）。没上场的人，现有的本地人物 AI（`TM.NPC.LocalAI`，不调模型）和性情打分照旧，也就是主稿 5.6 节的三层。实存档有 205 个活人，上场的是一小部分。

### 7.4 每人看到什么

每人的请求就是 `brief` 的完整档，加上这段时日他知道了什么：

- **亲历的事**（卷里点了他的）：看经过。
- **别处的事**：只听风声，按路程算传没传到（卷的「风声」段，`TM.MapRouteDays`）。
- **收到的信和回报**。

**不带 5.48 万字的固定部分**：那里面有别人的隐藏议程和危机分岔，都是这个人不该知道的。规矩只带和扮演有关的：时空约束（`_buildTemporalConstraint`）、称谓、朝代文风。所以每人的请求约 6000～10000 字〔初值〕，比旧的专精调用小一个量级。

**一个要改的地方**：`getMemoryContext` 现在给每个人都塞天下大势（货币、户口、央地财政……，`tm-mechanics-memory.js:745` 起）。他不该全知道。人物层先按职位裁（户部尚书知国库，皮岛的毛文龙不知）；问对等其他场合跟着改，比过再定。

### 7.5 每人交什么

下面的内容取自 09-21 的真实输出，格式是示意：

```
<<<人 崔呈秀
心里想：客氏一夜下狱，京营又交了节。新主行事沉鸷，不是先帝。眼下第一要紧是那几本边饷虚冒的册子。
做：
{"act":"conspire","plan":"夜遣心腹校尉潜往户部直舍，销毁边饷虚冒册籍","why":"掩盖历年克扣辽饷","public":false}
{"act":"private_correspondence","to":"魏忠贤","content":"厂公明鉴：客氏昨夜已被收系诏狱……厂公宜引罪乞退，推让印柄……","public":false}
对人：
{"who":"魏忠贤","dir":-1,"deg":"中","why":"危局之下，疑他弃己求活"}
记：客氏下狱，京营交节失据，须防科道交章
人毕>>>
```

规矩：

- **只写打算做什么，不写结果。** 成不成不归他定。
- **可以什么都不做。** 静观、等待、拒绝都是选择（现有提示词已允许）。
- **结构不能跳。** 每人必交「心里想」和「记」；「做」可以空，但空要是他的选择，不是模型偷懒。广度靠这个结构和 7.3 节的名单逼出来，这是 Agent 模式的教训。
- **可以冲着玩家来**：上疏、求见、请款，按路程送到案头。

### 7.6 他做的事接到游戏的哪里

人物层不另开一套，他的「做」都落到现有机制上：

| 他做的事 | 接到 | 回来什么 |
|---|---|---|
| 上疏、弹劾、请款 | 奏疏系统，按路程到玩家案头 | 批复进他的记忆 |
| 求见 | 求见队列 | 召对时面对的就是这个人 |
| 写信 | 鸿雁，按路程送达 | 对方读到，上场时可回 |
| 举荐、任免（有权的） | 官制写口，查权限 | 回执 |
| 动兵、练兵、修城 | 军令与军队账（`tm-command-authority.js`、行军） | 裁决定结果 |
| 动钱 | 公库、私产（`TM.PoliticalActions`、人物经济） | 回执 |
| 结党、串联、密谋 | 党派账、阴谋系统（`tm-conspiracy.js`） | 裁决定结果 |
| 提议题 | 廷议待议（`GM._pendingTinyiTopics`） | 朝议时他是发言人之一 |
| 势力行动 | 外交、战争、势力账 | 裁决定结果 |
| 家事、交游 | 家族、婚姻、日常往来（`TM.NPC.DailyActivities`） | 回执 |

这些大多是现成的：`NpcBehaviorRegistry` 里 30 来种行为各有处理函数，`ActionLedger.execute` 统一查身份、权限、钱。现在的 `executeNpcBehaviors` 模型调用并入人物层，不重复。逐项接没接通，放在人2 普查（第十五章）。

### 7.7 谁定结果：裁决

**人只声明，世界定结果。** 「AI 的说法只算声明」这条铁律在这里同样适用。代码先过一道门（身份、权限、钱，沿用行动账），然后分两类：

- **只关乎自己的**：写信、打探、转移私产、静观。过了门就算数，信按路程排进时间线。
- **碰到别人或动硬账的**：动兵、密谋、弹劾、索饷、邦交。交给裁决。

裁决像桌游的主持人：一次全知的 AI 调用，读全部声明和要事的卷，带完整的固定部分和规矩，逐条定：谁和谁撞上了、成没成、损失多少、谁察觉了。旧 sc18、sc1c、sc16 里的硬核规矩搬到这里，军事伤亡、势力互动都由它写实数。账行走同样的落账和回执，断了也接着办。

比如崔呈秀要销毁册籍，而王承恩正在封存档册：裁决可以定成「烧了一半，被方正化的人撞见」，于是生出一条风闻「兵部尚书私宅夜开便门」（这是示意）。

**人物层只走一轮，裁决也只一次，不递归。** 当事人知道结果、读到来信，是下次推演的事。这样时间是顺的，也不会无限连锁。

裁决同时提新事（过生事闸，下次推演才办）和留伏笔，v2 的「统览」并进这里。生事闸沿用主稿 2.1 节：类型在目录内、数额在账本承受范围内、利害人在册；没有账本佐证的标「风闻」。入册上限沿用主稿 12.10 节：每 30 日 3 件，一次至多 9 件。

### 7.8 没有人的东西

百姓、天灾、物价、阶层情绪没有一个具体的人可扮：

- **阶层**：有领袖的（士大夫有韩爌、军户有孙承宗、流民有王嘉胤），领袖自己上场；阶层整体的反应和没有领袖的阶层（自耕农、工匠）由裁决写方向、程度、原因。
- **地方民情**：裁决写方向、程度、原因，代码折算。
- **天灾、物价**：引擎算。
- **风闻**：从人的行为里长出来。被察觉的行为变风闻；造谣也是一种行为。
- **文人诗作**：不动账，放后台，或打开文苑时生成，作者走 `brief`。

### 7.9 产量基线

**这张表就是对照实验的基线。**

| 09-21 真实一回合的产量 | 新的来源 |
|---|---|
| 16 条暗手、6 条阴谋、1 次阴谋推进 | 各人的「做」 |
| 7 条心绪转变、5 条关系变化 | 各人的「心里想」「对人」 |
| 4 封来信、3 封私信、8 条私下往来 | 各人的「做」 |
| 16 条势力暗流、8 条优先、6 条行动、5 条指令、5 条互动、5 条事件、3 条决断、4 条关系、2 条邦交 | 势力首领或代言人的「做」，裁决定结果 |
| 19 条军事行动、3 条军队增减、1 项招募、态势、边患、士气 | 主帅和首领的「做」，裁决定伤亡和账 |
| 4 条党派动作 | 党魁的「做」 |
| 5 条阶层反应、4 条地方、13 条风闻 | 裁决 |
| 4 篇诗文 | 后台 |

现有的深度档（精简、标准、完整）继续有效，决定上场多少人。

## 八、成史

### 8.1 它就是现在的时政记调用，只换了输入

现在的时政记（sc1d）本来就是主推演之后单独写的，输入是 SC1 的声明（`tm-endturn-ai.js:3975-3996`），并不看回执。**成史沿用它的提示词和手艺，只把输入换掉**：

- 视野内的回报（8.2 节）；
- 回执摘要；
- 人物层和裁决产出中已传到的部分；
- 视角人物亲眼所见、亲手所为；
- 最终数字；
- 上一篇时政记的末段（接文气）。

账上没有的硬事实，它根本看不到。「说的和数据对不上」就这样从输入上断掉，而不是事后再查。

### 8.2 只写已传到的事

每条回报都带发出地和事发日。代码用 `TM.MapRouteDays` 算到达日：

- **到达日 ≤ 今日**：进这次的史记和案头；
- **到达日 > 今日**：排进时间线，到了才进案头，下次史记才写。

京师里的事当日可知；陕西的事要等驿路。第一篇时政记因此不再全知：东江毛文龙暗中截留，朝廷未必此刻知道。同志定的就是要这个悬念。

**一个要同志留意的变化**：现在的时政记是全知的，暗流也写。改成只写已传到的之后，单篇时政记会比现在短、比现在「知道得少」，暗中的事要等风闻和密报。这正是拍板 9，盲读时不要误判为「薄」；要比的是总体的世界感。

`经过` 是实情，存在事里，给世界层和下次办事读，不给成史。这也是主稿 13.2 节两层的落地：**世界层就是卷、人物层和裁决，视角层就是成史**。将来视角人物换了，同一批事可以按新人物的视野另看。

### 8.3 实情和呈报

回报可以和经过不一致：胡廷宴可能报「渐有头绪」。AI 按这个人的动机写，史记就写「胡廷宴奏称……」。真相留在 `facts.actual`，日后可能被巡按揭出。

这一版只允许**文字**虚报。数字上的失真继续走现有的奏报失真层（封顶 35%），不新开一套。

### 8.4 一次写成

一次调用写完，产出分段，每段有开有合：

```
<<<时政记 ... 时政记毕>>>
<<<实录 ... 实录毕>>>
<<<史臣曰 ... 史臣曰毕>>>
<<<摘要 ... 摘要毕>>>       标题、一句话摘要
<<<近况 ... 近况毕>>>       视角人物的处境与内心
```

下游只要这一组字段，已由 `TM.Endturn.ModeContract.normalizeResult` 定死（`shizhengji`、`shiluText`、`turnSummary`、`szjTitle`、`szjSummary`、`playerStatus`、`playerInner` 等），所以渲染和史记册不用改。

断在哪段，就从哪段的上一自然段接着写。

### 8.5 写完再核一遍

代码用现有校验器（活人一致性、任免、钱粮数额，`tm-ai-narrative-guards.js` 与 `validators.js`）扫一遍成文：

- 对不上的，退回那一段重写 1 次；
- 再对不上，保留原文并标「史笔待核」，界面可见。不再静默。

叙事审读（sc27）和史实核对（history_check）照旧留在成史之后，先留后裁。

### 8.6 后人戏说和来文

- **后人戏说**：点开才生成，读的范围和史记相同，不剧透没传到的事。
- **奏疏来文**：回报是短报。显著度靠前的几件，到达前在后台写好全文（主稿 12.3 节）；其余打开时才生成。

## 九、记忆

LLM 模式的记忆调用（`sc_memwrite`、`sc07`、`sc25c`）是跨回合连贯的根基，也是 Agent 模式丢得最狠的部分。

**第一版这几个调用全部保留在推演后台**，只把输入从「SC1 的声明」换成「卷、人物声明和裁决结果」。人物认知（`GM._npcCognition`）还要供问对读，不能断。

**另外加一层，不调模型**：

| 产出 | 写到 |
|---|---|
| 人物的「记」「心里想」 | `NpcMemorySystem.remember`、`innerThought`：他用自己的口气记自己的事 |
| 卷里人行的 `mem`、`feel` | 同上 |
| 经过 | `matter.volumes`，相关人物的下次案卷自然读到 |
| 回报 | 视角人物的记忆 |

人物既然自己记，也只记他知道的事，`sc_memwrite` 和 `sc07` 以后很可能可以减掉。减哪个都要比过。

## 十、即时制

本章替换主稿 12.7、12.8 节。

### 10.1 一次推演覆盖什么

**自上次推演以来发生的一切**：玩家下的令，确定性事件，人物和势力的动向，到期的事。不再有「这回合」。

要事的开销跟事的多少走：刚推演完马上再按一次，案上只有几件，花不了多少钱。上场的人数按距上次推演的日数折算：刚推演完再按，只有真收到新消息的人才上场。所以主稿拍板 12「推演不设下限」仍负担得起。

### 10.2 时间不倒流

- 账一律从按键当日起生效。
- 经过可以回溯着写（「八月二十四夜……」）。
- **已记录的是既成事实。** 案卷列出相关人物最后一次留下记录的日子，代码校验：
  - 写某人第 12 日已死，但他第 40 日被召见过，这条退回；
  - 远方的人，最后记录在此前，可以写成「早已卒于途，今日讣至」：死亡账从今日落，事发日记为过去。
- 带事发日的账行，事发日早于「最后记录日」的，一律退回。

### 10.3 诏令在路上

诏令按路程走（`TM.MapRouteDays`，主稿拍板 7）。按推演时还没到的诏，这件事不调模型，代码直接记「诏书在途，预计某日到」。

### 10.4 结果分批到达

- **回报、来信、奏疏**：按路程排进时间线，接着走时间陆续到。
- **定时生效的后果**：工程完工、官员到任这类，账行可以带未来日期（`effectiveDay`）。到了那天由时钟触发，**再校验一次依据还在不在**（那个人还活着、那支军队还在）。不在了，这一条作废，事重新进案。

### 10.5 两次推演之间

小调用（问对、朝议、私书、票拟）照常实时跑，结果变成事的材料，进下次推演。问对结束时现有的承诺提取照旧跑，开卷再通盘看一遍。

将来可以更进一步：消息一到，这个人就在后台动起来，不等按键（主稿 12.3 节）。这样按推演时要等的会短很多，也更像 CK3。第一版先不做，代价是他要反应的事可能已经过时。

### 10.6 回合是特例

新推演从第一天就按「自上次推演以来」写。回合只是「走满一节就推演」的特例：

**旧界面的过回合 = 节首 → 节尾（引擎）→ 推演 → 来文。**

`GM.turn` 在节尾加一，史记归到玩家下令的那一回合。这个顺序的代码路径 Agent 模式已跑通（`tm-endturn-agent-mode.js:926-935`、`resolutionTurn`），这只说明管线走得通，不说明质量。

时钟上线时只换触发方式，推演本身不用重写，主稿的时3（提示词时段化）在移植提示词时一并做。

**引擎先走的后果**：

- 减税这类要靠引擎才见效的诏令，要到下一节才在数字上体现。AI 写的硬账当场落。
- 现在有些系统在同一回合内读 AI 刚写的结果（如 `npcIntentAnalysis`、`partyDynamics`，主稿附录二），引擎先走后，它们要晚一节才读到。实验和试玩时要看手感。

玩家这回合的确定性动作照旧在引擎之前落地（`_applyAgentDeterministicInputs` 的做法）。

### 14.3 通过线

优先级从高到低。前四项正对着 Agent 模式的四样毛病：文气差、写得薄、世界不动、数据乱；第五、六项验人物实体。

| 项 | 通过线 |
|---|---|
| **文气与活气** | **同志盲读**：同一回合新旧两份成品（时政记、实录、来信、风闻、朝野动向、军情）匿名为 A、B，读完再揭晓。同志判定新的不差 |
| **产量** | 7.9 节各项条目数不低于 LLM 模式的七成〔初值〕。只是辅助指标，数量够不等于好 |
| **世界动没动** | 比推演前后的存档：人物、势力、地块、军队、变量里真有变化的数量，不低于 LLM 模式的七成〔初值〕 |
| **数据不乱** | 成文里的硬事实和回执对不上的 = 0（LLM 输出用同一方法计数作对照）；存档体检（死人在任、一职多人、账本不平、军队归属错乱）的问题数不多于 LLM 模式 |
| **人格统一** | 挑 3 个上场的人，推演后用问对、奏疏、书信各试一次，同志读：是不是同一个人；他知不知道自己暗中做的事，该瞒时瞒不瞒 |
| **不串味** | 代码查：人物的请求里没有他不该知道的事；再抽查声明，有没有写出他不该知道的 |
| **稳** | 截断、断流、拒答、401、坏行、中途退出，全部按 6.2 节行事，不丢已办、不重复落账（用桩模型测，不花钱） |
| **连贯** | 三回合连读无前后矛盾；第 2、3 回合确实接上了第 1 回合的卷 |
| 省 | 不设硬线，如实记录请求字数和耗时，和第十二章比 |

**不过怎么办**：

- A 的文气或活气不过：改提示词和结构再跑。**两轮还不过，说明按事办这条路本身会变薄，停，回桌重议**，不硬上。同志定过的「不要补丁」不等于一定要走这条路。

## 十六、风险

| 风险 | 对策 |
|---|---|
| **重蹈 Agent 模式：世界变薄** | 最大的风险。保留输出结构、提示词手艺、输出额度；上场名单和必交项逼出广度；A 组只换组织方式，先过盲读才往下走；两轮不过就停 |
| **人物各说各话，裁决接不住** | 裁决带完整规矩；一次定几十条，走续调用，分批不丢；实验专门读裁决 |
| **人物都按兵不动，世界还是不动** | 7.9 节产量基线和存档比对会查出来；提示词里写明他的处境和压力；再调选人 |
| **调用次数多，中转限速或按次计费** | 可改几人一批（G 组）；并行路数可调；429 只等待不算失败 |
| **`brief` 改动面大，伤到问对等现有手艺** | 以问对版本为底；一个机制一片，每片回归；可以先只给人物层用 |
| **按事办，丢了通盘感** | 默认一次调用办完全部要事；开卷统一判断；成史一个作者一次写完 |
| **文气变散** | 成史沿用现在的时政记提示词；经过不直接给玩家看；盲读把关 |
| **单篇时政记变短、变不全知**（拍板 9 的自然结果） | 同志盲读前先知道这一点；世界感由上场的人物和陆续到达的来文撑 |
| **代码立案漏了该办的事** | 裁决可以提新事；开卷可以指出漏了什么；实验里拿旧输出比，看漏了哪些 |
| **小批下旧落地代码的隐含假设** | 它是按「一回合一次」写的。头尾已知要拆；其余靠 LLM 模式的全量 smoke 和逐字段小批回归查 |
| **大存档快照太慢** | 绍宋实测；太慢就只拍涉及的根字段 |
| **弱模型不守格式** | 坏行只坏一行；全错时重申格式、减批；模型真不行就 3 次后留案。实验用同志的模型实测 |
| **续调用烧钱** | 花钱的调用有上界（6.3 节）；界面显示用量；可设上限 |
| **两套路径并存期变更翻倍** | 并存期只修 bug 不加功能；落地代码新旧共用；推6、推7 尽快接上 |
| **旧档** | 适配器无状态，第一次推演时把旧账读成事；`GM.matters` 缺失时自动建 |
| **引擎先走改变手感** | 已拍板；回报里写明「下月始见」；试玩时专门看 |

- **读结果时要记得的两组差异**（查账目实变时发现，没改）：诏书里规则能办的部分（补饷、任免、建军、赏赐等，`applyEdictActions`），A 组借用的 Agent 入口在推演之前就落地（`tm-endturn-agent-mode.js`：「确定性玩家输入必须先落地，再让模型观察真状态」），LLM 模式在推演之后的 post-ai-edict 步才落。所以两组 AI 看到的国库不同：第一回合的诏书含补发欠饷，A 组推演前太仓银已被补饷扣到 0（桩跑可见：其后一笔赈银拨不出），LLM 模式到史官成文时补饷还没扣（回放可见）。这一栏的财政差别有一部分出自先后，不全是组织方式。
- **接着修掉的**（同志：看过没修的去修，修好后统一推 main）：
  1. AI 财政条目的另一种写法（`{subject:"太仓银库", action:"拨发陕西急赈", amount:-100000, note}`，玩家 09-21 那局的主推演就这么写）原来整条判缺目标剔掉。现在在严格预检和落账入口就地改成标准形状：账户认太仓、国库、户部与内帑、内库，金额为负即支出，为正看字面（拨发、赈济为出，征收、鬻卖为入），认不准的照旧剔，不猜；同批央地调拨若是同一笔钱（同账户、金额差 1% 内、调拨的地名出现在这条里），这条跳过并留痕，不扣两次。
  2. sc27 叙事审读（默认关）：原来让模型把最弱的段落重写一遍，连同补充细节整段接在正文后面，原段和重写段并存；收尾时又被 sc2 原文盖掉。现在要模型原句照录：改句就地替换，增补接在指定句后；照录不准、出自诏令原句的一律不改；改动同时落到 sc2 结果，不再被盖回。
  3. 叙事模块（`tm-ai-change-narrative.js`）地块与区划互认：名字去后缀也算（地块「陕西」↔ 区划「陕西布政使司」），认不出再认省级区划自带的 `regionId`；府州只带 `mapRegionId`，不拿它认，免得把府里的事记到整省地块上；地方主官镜像用同一种认法。
  4. 修第 1 条时查出：严格预检的区划认定只认 id 和精确名，「陕西省」在预检就被剔，落账那边的宽松认法轮不到。现在区划在精确名一个都没有时，按落账同一规矩去后缀再认；重名照旧报歧义。

- **断处接着写**（同志 11-08 定：「玩家也会用这种中转，应该修……失败后应该要能在失败继续处自动续」）。原来的「对清单续办」是整卷重办：被掐的那一卷作废，下一次调用从这一卷开头重写，遇上 3 分钟就掐的中转，长卷永远写不完。实验台 A 组（办事、裁决两张清单）现在这样办：
  1. 中转回空（正文不到 5 字）就原样重发，隔 10 秒起、每次翻倍，最多 3 次。
  2. 被掐断（结束原因不是 stop）时，最后一个「毕>>>」之后的半截留下。下一次调用把半截接在助手那条末尾，叫它「从断处接着写，不要重复已写的内容」，并列出还没交的卷。拼接时去掉续写开头与半截结尾重叠的字（4 到 400 字）；续写若重起这一块（先写了「<<<」），半截作废，用新写的。
  3. 写疯了先收拾：同一块里同一行（15 字以上）出现三次以上、16 行内又出现的，只留一轮；一行超过 3000 字的，截到行内开始重复处或 800 字（取早的），退到最近的标点。正常交卷最长一行 870 字，这两场写疯的一行有 11674 字、33957 字。若正文就停在疯处，续写时叮嘱「这一栏不要再续，从下一栏接着写」。
  4. 半截接了 3 次仍没收尾就作废，记一次没办出；调用总数上限不变（件数×6）。
  - 试过的：离线自测（11-06、11-08 的正常交卷原文一字不动；两份写疯原文被收拾且判为停在疯处；拼接、作废、上限、回空重发都按预期）。桩跑在每张清单第一次调用的第二个「经过：」后强行掐断：办事三次交齐（1、2、5 卷），裁决两次交齐（1、24 块），接缝无重复。真模型还没跑。
