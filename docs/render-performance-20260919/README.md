# 天命渲染性能实查与局部修复（2026-09-19）

## 已确认并修复：编辑器栅格显示缓存
`web/map-editor-rastermaps.js` 原先用 `_dirty`（尚未保存）控制地形着色及高度热力图缓存，造成编辑后每次刷新重新分配画布并遍历全图；编辑后先保存再刷新又可能误用旧显示。
现使用独立 WeakMap 显示缓存，核对版本、数据引用、原画布、尺寸和可显示的调色板颜色；公开 rebuildCanvas 主动失效。保存状态不被显示操作清除，缓存不进入场景 JSON。
本轮运行时差异仅此文件：29 行新增、2 行删除。通过 Windows File.Replace 原子替换安装，原始文件备份保留。
新测试 `node web/scripts/smoke-raster-display-cache.mjs`：原版 3 通过 / 10 失败；补丁与安装后的源码均 13/13 通过。相同未保存内容连续 60 次显示调用，整图颜色转换从 60 次降为 1 次。
覆盖保存时序、数据替换、原地重建、尺寸变化、源画布替换、调色板变化、异步图片解码、缓存不持久化，以及两类图层全部 256 数值的 RGBA 输出一致性。
现有 `node web/scripts/smoke-editor-renderall-resilient.js`：15/15 通过；该现有测试主要是静态渲染器隔离守卫。`git diff --check -- web/map-editor-rastermaps.js` 通过。

## 已复现、尚未修复：正式大地图的无变化刷新
隔离且禁止联网的 Electron 实例加载真实 `web/index.html` 和官方绍宋剧本，1600×1000 隐藏窗口，566 地块。连续 12 次同步调用 `renderFormalMap()`：338.5–903.5 ms，中位数 352.8 ms。
SVG world 节点保持同一对象，主线程布局统计 layouts=0、rasterCells=0，705 项地名布局已经缓存；因此这段慢刷新不能归咎于当时重新逐像素计算地名布局。
12 次刷新仍产生 264 条 DOM mutation records（其中 72 条 childList）；活动地图 0 canvas、1143 path，HTML 字符数 22,766,949。
证据：`before/report.json`、`before-stdout.log`。这些是一次本机隔离实例的函数调用耗时，不是 FPS，也不是其他设备的通用性能结论。
首次探针在取得上述刷新数据后，因测试脚本调用未导出的相机函数而结束失败；相机测量无效，未当作验收通过。随后已纠正探针，但第二次 CPU 采样因磁盘满被停止，未取得完整 profile。
本轮没有修改 `phase8-formal-map.js`；尚未完成主要耗时归因或正式地图性能修复，不能声称整体卡顿已解决。

## 存储异常与操作边界
测试期间实际出现 ENOSPC；随后系统查询确认 C 盘 Free=0。仅删除本轮自建的隔离 userData/sessionData 缓存，停止本轮 Electron 探针；未扫描或删除玩家存档、密钥、私人文件。
最后一次复查 C 盘可用 337,809,408 字节（约 322 MiB），仍然紧张；可用空间持续变化，不能将其恢复全部归因于约 5.8 MB 的自建测试文件清理。
没有证据能将此前所有卡顿归因于磁盘满，但它已实际阻断本轮文件写入和后续分析。
所有现有其他窗口改动保留。未提交、推送、部署，未修改剧本数据、推演机制或 AI 质量设置。

## 后续优先级
先解决 C 盘空间紧张，再完成正式游戏 CPU / Paint 采样，区分无变化刷新中的归属查询、状态派生、搜索框和图例 DOM 改写成本。无需因为存在 SVG、Canvas 或栅格采样就直接重写为 WebGL。
