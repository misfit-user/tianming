这次补齐的核心流程是：**完整生成原文 → 判断应发生的变化 → 对照已执行状态 → 修改 → 读取真实前后值与实际差异 → Agent 再判定是否正确。**

## 输入完整性

- 时政记、实录及其他回合文本按完整字符串送入，不再只提供前 12000 字符。
- 同时收集本回合其他生成结果、原始诏令、起始核心变量、已执行回执和可查询的世界状态。重复原文使用显式来源引用去重；已有原始 API 回答也保留为可查询证据。
- 后续推演生成的新实录、正文、NPC、军务或财赋结果会触发补核，即使初核计划是“无需修改”。同文但属于不同后续来源的结果也会补核来源身份。
- 原始生成文本和 Agent 查询时读到的旧状态保留为独立证据，不会被后来的修改覆盖。原文未完整送达或预算不足时不能宣称核验完成。

## 实际修改与再核验

- 每项操作必须给出预期结果 postconditions，包括字段期望值、增量、应存在的记录或删除条件。常见字段修改与财政写入还自动补充目标字段、账本和余额镜像的检查。
- 正式写入口返回成功后，程序重新读取真实字段。返回成功却没改、改成错误值、只改了镜像等情况，不能凭接口回执放行；整组不合格修改回滚并交回修订。
- 复用原子写入口已持有的修改前快照，计算实际 GM/P 业务数据差异，供 Agent 查看预期之外的改变，不额外复制一份整个世界。
- 修改后另有 Agent 核验步骤：同时看到对应完整原文、操作意图、真实前后值、实际差异和当前结果，逐笔判断是否改对。发现误改或遗漏可以继续提交剩余修正，再核验；不得重复已完成的扣款。
- 回合文本修正同步到正式 record 与相关结果字段；生成时的旧原文仍保留为核验依据。
- 后台记忆任务延后至复核结束启动，避免在修改后核验期间覆盖被检查状态。最终提交要求 approved、verified 和完整原文覆盖回执。

初核仍与后续推演并行。修改后的判断依赖真实写入结果，必须在写入后执行；该步骤和必要的补核计入同一次预算，不承诺零额外等待。
