# LLM 模式「断处续」方案（11-08）

同志 11-08 定：玩家也会用「写到几分钟就掐」的中转，主推演这类长调用被掐时，把半截 JSON 交回去接着写，不再中止回合。本稿先摆桌，同志定了才改游戏：定的见第六节，实现见第七节。

## 一、现在被掐了会怎样

以 11-08 真跑 `auto-1108-1421` 的 LLM 组为例（deepseek-v4，新中转）：

1. 主推演 sc1 走 `_callEndturnAI`（非流式），中转在 272 秒掐断，回了 18241 token、41497 字，JSON 停在 `party_changes` 里「阻止东林」半句。中转报的结束原因却是 `stop`。
2. 解析走 `_parseOrRepairJsonResult` → `TM.RecoveryRuntime.parse`。应急恢复默认开着（`mode:'auto'`），见到截断（`_looksJsonUnclosed` 为真，或结束原因是 length）就直接拒收，不拿「补全括号」凑出来的对象。这是 07-04 定的规矩，防「中段账目蒸发」。
3. 拒收后走 sc1 救援小调用（3500 token 上限，只记最低限度的账），这次救回的是空架子。
4. `finalSC1` 在普通重试没用完时跳过 → 抛「主推演未形成完整结构化结果；保留响应并中止本回合」。玩家只能手动重来，重来多半又在同一处被掐。

同一回合 sc1c（势力互动）也在 244 秒被掐（报 length）。sc1c 失败不影响主流程，可这一回合的势力往来就没了。

## 二、要改成怎样

被掐的那次回答不扔：原样当作助手说了一半的话，再发一次请求，请模型从断处接着写；把两段拼起来，拼出完整 JSON 再交给原来的解析。拼得出就照常往下走，拼不出才走原来的拒收、救援、中止。

### 1. 接在哪里

`_callEndturnAI`（`web/tm-endturn-ai.js`）里，拿到回答之后、`_parseOrRepairJsonResult` 之前。回合里的子调用都经过它：sc0、sc05、sc1q、sc1、sc1b、sc1c、sc1d 直接调；sc15、sc16、sc18、sc2、sc07 经 `_callFollowupAI`（`web/tm-endturn-followup.js`）转进来。一处改动全覆盖。

只接 JSON 回答：去掉代码块标记后以 `{` 或 `[` 开头的才算。纯文字回答不接，因为看不出它写没写完。

流式那条路（`P.ai.stream_sc1`，默认关）收完流后也接同一个函数。

### 2. 怎么算「被掐」

回答里的 JSON 开了头、没收尾（沿用现成的 `_looksJsonUnclosed`），不论中转报的结束原因是什么。中转把掐断报成 `stop` 的情况，这一条也认得出来。

不算被掐的：

- JSON 收了尾、只是中段写错：接着写也救不了，照旧走修复。
- 正文一个字没有（比如 11-08 那次思考了 247 秒、正文没写就被掐）：没有可接的半截，照旧整次重来。

### 3. 接着写的请求

- 消息：原来的系统、用户两条照旧；后面加一条助手消息，内容是被掐的回答原文（一字不改）；再加一条用户消息：
  > 你上一条回答在「……末尾 30 字……」处被截断了。请紧接着最后一个字符往下写，把这个 JSON 写完：不要重复已写的内容，不要从头开始，不要加解释或代码块标记。
- 去掉 `response_format`（json_object / json_schema）。这两种模式要求输出一个完整对象，模型就写不出「后半截」。模型、温度、输出上限、思考参数照原请求。
- 前面的消息原样不动，支持缓存的接口（DeepSeek、Claude、OpenAI）大多命中缓存。

### 4. 怎么拼

依次试，哪一种拼出来的能解析就用哪一种：

1. 去重叠：续写开头常重复上文最后几个字或最后一行，去掉 4～400 字的原样重复再接。
2. 它从头重写了整个 JSON（续写以 `{` 开头，自己就能解析且带主字段）：用新写的。
3. 断在一个值的半中间，续写把这个值重写了：退回到半截里最后一个完整元素之后（最后一个结构上的逗号），再接。

拼完再判一次：

- 能解析：完成。
- 还是没收尾（又被掐）：接着发下一次。
- 中段坏了：放弃，走原来的路。

### 5. 上限与记账

- 同一次调用最多接 3 次。
- 接着写的请求另记账：调用编号记成 `sc1:cont1` 这样，进用量统计。不占普通重试的次数，不触发应急恢复的「重试已用尽」。这一点要对着 `TM.RecoveryAdapters` 的记账细核，见第四节。
- 总时长受同一个回合期限管（`sc1RecoveryDeadline`）。

### 6. 玩家看得到的

- 加载提示：「主推演被中转截断，正在从断处接着写（第 1 次）」。
- 回合诊断里记一条：哪个子调用、接了几次、各段多少字、成没成。
- 设置里加一个开关：「回答被截断时从断处接着写（最多 3 次）」。这是新的开关，按规矩要配设置项。

## 三、代价

- 每接一次，整份提示要重发一遍。主推演约 15 万 token；能命中缓存的接口花得不多，不支持缓存的中转每次按原价算，最坏是这一次调用的输入花到 4 倍。
- 接着写那次也要等中转把它写完：新中转大约多 1～2 分钟。

## 四、要核的

1. 应急恢复的记账（`RecoveryAdapters.normalMeta`、`markResponse`、`assertNormal`）认的是第一次回答的 data 对象。拼好的正文就地写回这个对象（内容、结束原因），不另造对象。还要核：接着写的请求另走一条记账，会不会被它当成「绕过普通重试」。
2. 「保留响应」（`TM.Endturn.ResponseRecovery`，玩家重试同一回合时复用完整回答）存的应是拼好的完整回答，不是半截。
3. 超大响应封顶（桌面 1MB、安卓 384KB）对拼好的总长照样生效。

## 五、怎么验

1. 单元冒烟（`web/scripts/`，node 跑）：被掐判定、去重叠、从头重写、断在值中间、报 stop 却没收尾、代码块标记、接 3 次仍没收尾。另外跑现有的应急恢复和重试冒烟，确认没碰坏。
2. 实验台假中转：给 LLM 组加一个「在第 N 字掐断、结束原因报 stop/length/空」的桩，用 11-08 主推演的真回答切开，走完整回合，验拼好的 JSON 与原文一致、回合正常推进。不花钱。
3. 定了再上新中转真跑：LLM 组与 A 组一起跑三回合。

## 六、同志定的（11-08）

1. 范围：回合里所有 JSON 子调用一起加。
2. 默认开，设置里可关。
3. 同一次调用最多接 3 次。

## 七、实现（11-08）

- 新模块 `web/tm-ai-continuation.js`（`TM.AIContinuation`，只做文本与请求体，不写 GM/P）：
  - `isCut`：去掉代码块标记后以 `{`/`[` 开头、括号没配平（字符串里的括号、转义引号不算）。
  - `buildBody`：原消息加两条，去掉 `response_format`，不动原请求体。
  - `stitch`：依次试三种拼法，取结构没坏的那种。
    - 从头重写（第一个键相同）。
    - 去重叠（4～400 字）。
    - 退回到被重写元素的开头：续写以「"键":」开头就退到对象里这一项，否则退到数组里这个元素。
    - 「结构没坏」用补括号试解析判断，几种收法都试（断在值里、键里、冒号后、逗号后）；补出来的只用于判断，不当答案。
  - `run`：最多 3 次。
    - 续写回空可再试一次，第二次还空就停。
    - 拼坏了、出错、过了总期限，都停。
    - 收尾后去掉 JSON 之后的闲话。
  - `continueIfCut`：给回合推演用的接线。
    - 拼全了才就地写回原 data 对象，并把结束原因写成 stop。
    - 接着写的请求 id 记成 `sc1:cont1`，不带原调用的重试票；进用量统计和诊断（`recordAIDiagnostic('continuation')`）。
    - 加载提示：「主推演被中转截断，正在从断处接着写（第 1 次）」。
- `tm-endturn-ai.js` 只加 3 行：
  - `_callEndturnAI` 拿到正文后、超大响应封顶前调一次（子调用全经过这里）；
  - 主推演流式那条路收完流后调一次。
  - 这个文件是「只许拆不许堆」的巨石，基线 4934 行，现 5020 行，在预算内。
  - 文件原是 CRLF/LF 混排（32 行只用 LF）：插入行按所在处的行尾写，原有字节不动。
- 设置面板（`tm-patches.js`「性能·成本控制」）：「回答被截断时从断处接着写（默认启用）」，`P.conf.aiContinueOnCut`，关了就照旧。
- `index.html` 登记在 AI 基础设施（json → infra → model-detect）之后。启动清单、原生准备清单重新生成；热更基线就地补了 6 条哈希，新增 1 条（没有用 sync-hot-baseline --write）。

## 九、11-08 真跑查出两处误判（已修）

19:21 在新中转真跑 `auto-1108-1921`（deepseek-v4）。第一回合 LLM 组触发了两次断处续，看原文都不是被掐，是模型自己把 JSON 写坏了：

1. 统筹思考（sc0）218 秒、报 stop，结尾写成 `"moves":[[]}}`，多了一个 `[`。旧判法只数括号层数、不分方括号和花括号，当成没收尾，接了两次：
   - 第一次模型回 `"]}}`，被拼法③退进对象，收成一个叫 `]}}` 的新键；
   - 第二次拼坏了才停。
   白发两次整份提示（各约 13.5 万 token），游戏随后照常整次重来，「正在从断处接着写（第2次）」在这 4 分多钟里一直挂着。
2. 主推演（sc1）78 秒、报 stop，在 tableEdit 一栏写成 `…-->"</tableEdit>",`，引号没转义。旧判法见一个引号就翻转一次「在不在字符串里」，扫到结尾还在字符串里，当成没收尾。接着写的那次正撞上中转余额用完（402）；就算余额够，也拼不出能解析的 JSON。
3. 第 2 条还牵出游戏原有的毛病：`tm-endturn-ai.js` 的 `_looksJsonUnclosed` 同样逐个引号翻转，把这份写坏的主推演当成截断。应急恢复见截断直接拒收，不走普通重试，接着就是救援、中止本回合。有没有断处续都一样。

改法：

- 判「被掐」加两条，都属于写坏：
  - 括号要配对：`}` 只能收 `{`，`]` 只能收 `[`，配不上的算写坏；
  - 字符串收尾的引号后面（跳过空白）只会是 `, : } ]` 或到头，后面跟着别的字的，是没转义的引号。
  写坏的不接，交原来的修复与重试。已写的部分还要「补上括号就能解析」才接；断在 true、数字、转义符半中间的也补得上。
- 拼法③只认一种对应：续写以「"键":」开头才退进对象，否则只退进数组。从头重写的那份自己也要结构没坏才用。
- 接完把加载提示还给原来那句；别的调用改过提示就不动。
- `_looksJsonUnclosed` 用同一条引号规则：没转义的引号不再当成截断，写坏的回答走普通重试，重试用完再交应急修复。真被掐的照旧算截断。

验过：

- 真跑原文：
  - 上面两份写坏的都不接，`_looksJsonUnclosed` 也不再把主推演那份当截断；
  - 14:21 那次真被掐的照旧要接；
  - 三份完整回答（11-06 主推演 16198 字、这次的 sc0 与 sc1q）在每一个字处切开，共约 2.6 万刀，每刀都判为被掐、都算截断。
- 单元冒烟 73 项，新加的几项：写坏不接，断在 true、数字、转义符半中间也认，拼法③不退进对象，加载提示还原，`_looksJsonUnclosed` 的引号规则。
- 实验台假中转：
  - 主推演第一次给这次写坏的那份：没去要接着写，应急恢复走普通重试，第二次拿到完整回答，主推演 48 个字段，回合推进。
